# Requirements Document: Clip Selection Improvements

## Introduction

The Clip Selection Improvements feature enhances the video highlight generator's ability to identify and select engaging, viral-worthy clips for social media platforms (YouTube Shorts, TikTok, Reels). The current system uses multi-phase scoring (text keywords, audio energy, LLM quality assessment) but suffers from context blindness, generic scoring rubrics, and rigid selection logic. This feature introduces context-aware LLM scoring, creator-specific calibration, improved boundary detection, enhanced audio analysis, and semantic deduplication to maximize engagement and minimize manual review time. All improvements work with data available at generation time: transcript, audio, video, and LLM analysis.

## Glossary

- **Clip_Selector**: The system component responsible for ranking scored segments and selecting the top N clips for export.
- **Scorer**: The system component that computes text, audio, LLM, spike, and burst scores for each transcript segment.
- **LLM_Scorer**: The subsystem that sends candidate clip windows to a local LLM (via Ollama) for quality assessment.
- **Context_Window**: A ~30-second transcript window centered on a candidate segment, sent to the LLM for scoring.
- **Creator_Profile**: A persistent data structure storing creator-specific metadata (content type, typical energy level).
- **Boundary_Refiner**: The LLM-based subsystem that identifies Setup → Moment → Reaction arcs and adjusts clip start/end times.
- **Audio_Analyzer**: The enhanced audio processing subsystem that detects laughter, screaming, and emotional vocal patterns.
- **Engagement_Predictor**: A heuristic model that estimates viewer retention (will viewers watch to the end?) based on clip features available at generation time.
- **Semantic_Deduplicator**: A system that detects semantically similar clips (beyond simple Jaccard similarity) using embeddings or LLM comparison.
- **Adaptive_Spacing**: A dynamic spacing constraint that adjusts based on video length and content density.
- **Hook_Detector**: A system that identifies viral hooks (opening moments that grab attention) in the first 3 seconds of a clip.
- **Reaction_Tail_Detector**: A content-based system that detects natural pauses or breath points to avoid cutting off mid-sentence.
- **Phrase_Detector**: A keyword system that matches multi-word phrases (e.g., "oh my god") rather than individual words.
- **Emotion_Detector**: An audio analysis system that uses pitch, volume, and spectral features to detect laughter, screaming, excitement, etc.
- **Visual_Analyzer**: A future system that analyzes facial expressions and on-screen action (not implemented in this spec).
- **Transcript**: The Whisper-generated speech-to-text output with timestamps for the source video.
- **Segment**: A single Whisper transcript segment (typically 3-10 seconds of speech).
- **Clip**: An expanded segment (20-100 seconds) selected for export, with start/end times and a score.
- **Viral_Potential**: A composite score estimating how likely a clip is to generate high engagement based on features available at generation time.

## Requirements

### Requirement 1: Creator Profile Persistence

**User Story:** As a content creator, I want the system to remember my content type and style, so that scoring is calibrated to what makes MY content engaging.

#### Acceptance Criteria

1. THE System SHALL create a Creator_Profile data structure for each unique creator or channel.
2. THE Creator_Profile SHALL store content type metadata (gaming, podcast, comedy, vlog, educational, etc.).
3. THE Creator_Profile SHALL store typical energy level (high-energy, calm, moderate).
4. THE Creator_Profile SHALL persist to disk (JSON or SQLite) and reload on subsequent runs.
5. WHEN a new video is processed, THE System SHALL load the Creator_Profile and use it to adjust scoring weights.

### Requirement 2: Full Video Context for LLM Scoring

**User Story:** As a user, I want the LLM to understand the full video context, so that it can identify moments that are interesting relative to THIS specific video.

#### Acceptance Criteria

1. WHEN LLM scoring is enabled, THE LLM_Scorer SHALL generate a video-level summary before scoring individual windows.
2. THE Video summary SHALL include: content type, main topics, overall energy level, key recurring themes.
3. THE Video summary SHALL be generated by sending the LLM a condensed transcript (e.g., every 10th segment or 1 segment per minute).
4. THE LLM_Scorer SHALL prepend the video summary to every Context_Window prompt sent to the LLM.
5. THE LLM prompt SHALL instruct the LLM to score moments relative to the video's baseline, not generic content.
6. THE LLM_Scorer SHALL cache the video summary to avoid regenerating it for every window.

### Requirement 3: Creator-Specific LLM Calibration

**User Story:** As a content creator, I want the LLM scoring rubric to be calibrated to my content style, so that scores reflect what works for MY audience.

#### Acceptance Criteria

1. THE LLM_Scorer SHALL use the Creator_Profile to customize the scoring rubric sent to the LLM.
2. WHEN the Creator_Profile indicates high-energy content (gaming, comedy), THE LLM rubric SHALL emphasize audio energy and reaction intensity.
3. WHEN the Creator_Profile indicates calm content (podcast, educational), THE LLM rubric SHALL emphasize semantic interest and insight quality.
4. THE LLM rubric SHALL adjust the 1-10 scale anchors based on the creator's typical content (e.g., "7 = good for this creator" vs generic "7 = good clip").
5. THE LLM_Scorer SHALL log the customized rubric for each video to aid debugging.

### Requirement 4: Phrase Detection for Keywords

**User Story:** As a user, I want the system to detect multi-word phrases like "oh my god" as a single keyword, so that scoring is more accurate.

#### Acceptance Criteria

1. THE Phrase_Detector SHALL support multi-word keyword phrases (e.g., "oh my god", "no way", "watch this").
2. THE Phrase_Detector SHALL match phrases case-insensitively and with word boundaries.
3. THE Phrase_Detector SHALL assign higher weight to phrase matches than individual word matches.
4. THE Phrase_Detector SHALL handle partial matches (e.g., "oh my" should not match "oh my god").
5. THE Phrase_Detector SHALL be integrated into the text scoring pipeline (compute_text_score).
6. THE Phrase_Detector SHALL log detected phrases for debugging.

### Requirement 5: Content-Based Reaction Tail Detection

**User Story:** As a user, I want clips to end at natural pauses, so that they don't feel cut off mid-sentence or mid-reaction.

#### Acceptance Criteria

1. THE Reaction_Tail_Detector SHALL analyze the Transcript to identify natural pauses (sentence boundaries, breath points).
2. THE Reaction_Tail_Detector SHALL extend clip boundaries to the nearest natural pause within a configurable window (e.g., ±3 seconds).
3. THE Reaction_Tail_Detector SHALL use punctuation (periods, question marks, exclamation marks) as pause indicators.
4. THE Reaction_Tail_Detector SHALL use silence gaps in the audio (>0.5s) as pause indicators.
5. THE Reaction_Tail_Detector SHALL prioritize natural pauses over fixed time-based expansion.
6. THE Reaction_Tail_Detector SHALL log detected pauses and boundary adjustments for debugging.

### Requirement 6: Enhanced Audio Emotion Detection

**User Story:** As a user, I want the system to detect laughter, screaming, and emotional vocal patterns, so that high-energy moments are prioritized.

#### Acceptance Criteria

1. THE Emotion_Detector SHALL analyze audio features (pitch, volume, spectral centroid, zero-crossing rate) to detect emotional patterns.
2. THE Emotion_Detector SHALL classify audio segments into emotion categories: laughter, screaming, excitement, calm, neutral.
3. THE Emotion_Detector SHALL assign an emotion score (0.0-1.0) to each Segment based on detected patterns.
4. THE Emotion_Detector SHALL integrate emotion scores into the audio scoring pipeline (combine_scores).
5. THE Emotion_Detector SHALL use librosa or similar audio analysis library for feature extraction.
6. THE Emotion_Detector SHALL log detected emotions and scores for debugging.
7. THE Emotion_Detector SHALL handle silent segments gracefully (assign neutral emotion, score 0.0).

### Requirement 7: Semantic Deduplication

**User Story:** As a user, I want the system to avoid selecting clips with similar topics or meanings, so that the output is diverse and not repetitive.

#### Acceptance Criteria

1. THE Semantic_Deduplicator SHALL compute semantic similarity between clip transcripts using embeddings (e.g., sentence-transformers).
2. THE Semantic_Deduplicator SHALL identify clip pairs with high semantic similarity (>0.8 cosine similarity).
3. WHEN two clips are semantically similar, THE Semantic_Deduplicator SHALL discard the lower-scoring clip.
4. THE Semantic_Deduplicator SHALL run after the Jaccard deduplication pass (as an additional filter).
5. THE Semantic_Deduplicator SHALL log discarded clips and similarity scores for debugging.
6. THE Semantic_Deduplicator SHALL be configurable (enabled/disabled, similarity threshold) via the Config object.

### Requirement 8: Adaptive Spacing Constraints

**User Story:** As a user processing short videos, I want the spacing constraint to adapt to video length, so that I don't end up with only 1-2 clips from a 10-minute video.

#### Acceptance Criteria

1. THE Adaptive_Spacing system SHALL compute an effective spacing constraint based on video duration and top_n_clips.
2. WHEN video_duration / top_n_clips < min_clip_spacing, THE System SHALL scale down the spacing constraint proportionally.
3. THE Adaptive_Spacing system SHALL log the effective spacing constraint for each video.
4. THE Adaptive_Spacing system SHALL ensure at least top_n_clips can fit within the video duration with the computed spacing.
5. THE Adaptive_Spacing system SHALL be enabled by default and configurable via the Config object.

### Requirement 9: Hook Detection for Viral Potential

**User Story:** As a user, I want the system to identify clips with strong opening hooks, so that viewers are grabbed in the first 3 seconds.

#### Acceptance Criteria

1. THE Hook_Detector SHALL analyze the first 3 seconds of each candidate clip for hook quality.
2. THE Hook_Detector SHALL use the LLM to classify hooks into categories: question, shocking statement, action, mystery, none.
3. THE Hook_Detector SHALL assign a hook score (0.0-1.0) based on LLM classification and confidence.
4. THE Hook_Detector SHALL boost clip_score multiplicatively for clips with strong hooks (e.g., 1.2x multiplier for hook_score > 0.8).
5. THE Hook_Detector SHALL log detected hooks and scores for debugging.
6. THE Hook_Detector SHALL be configurable (enabled/disabled, boost multiplier) via the Config object.

### Requirement 10: Engagement Prediction

**User Story:** As a user, I want the system to predict viewer retention, so that clips likely to be watched to the end are prioritized.

#### Acceptance Criteria

1. THE Engagement_Predictor SHALL estimate viewer retention (0.0-1.0) based on clip features available at generation time: duration, pacing, energy curve, hook quality.
2. THE Engagement_Predictor SHALL use a heuristic model (weighted combination of features) based on clip characteristics.
3. THE Engagement_Predictor SHALL integrate retention estimates into the final clip_score (additive or multiplicative boost).
4. THE Engagement_Predictor SHALL log retention estimates for each clip for debugging.
5. THE Engagement_Predictor SHALL be configurable (enabled/disabled, weight) via the Config object.

### Requirement 11: LLM Boundary Refinement Improvements

**User Story:** As a user, I want the LLM to refine clip boundaries more accurately, so that clips capture complete narrative arcs without cutting off reactions.

#### Acceptance Criteria

1. THE Boundary_Refiner SHALL provide the LLM with a wider context window (±60s instead of ±45s) for better arc detection.
2. THE Boundary_Refiner SHALL instruct the LLM to identify Setup, Moment, and Reaction explicitly with timestamps.
3. THE Boundary_Refiner SHALL validate LLM-suggested boundaries against natural pauses (from Reaction_Tail_Detector).
4. THE Boundary_Refiner SHALL reject LLM suggestions that cut off mid-sentence or mid-word.
5. THE Boundary_Refiner SHALL log LLM reasoning (REASON field) for each boundary adjustment.
6. THE Boundary_Refiner SHALL fall back to the original boundaries if LLM refinement produces invalid results.

### Requirement 12: Audio Spike Bypass Improvements

**User Story:** As a user, I want audio spike clips to be validated for engagement, so that loud but uninteresting moments are filtered out.

#### Acceptance Criteria

1. WHEN an audio spike clip is detected, THE System SHALL validate it using the Engagement_Predictor before bypassing LLM scoring.
2. IF the Engagement_Predictor estimates low retention (<0.3), THE System SHALL discard the audio spike clip.
3. THE System SHALL log discarded audio spike clips and their engagement scores for debugging.
4. THE System SHALL apply a minimum text score threshold to audio spike clips (e.g., text_score > 0.1) to filter out pure noise.
5. THE System SHALL be configurable (audio spike validation enabled/disabled) via the Config object.

### Requirement 13: Improved Deduplication Threshold

**User Story:** As a user, I want the deduplication threshold to be adaptive, so that it's stricter for short videos and more lenient for long videos.

#### Acceptance Criteria

1. THE Semantic_Deduplicator SHALL compute an adaptive similarity threshold based on video duration and top_n_clips.
2. WHEN video_duration < 30 minutes, THE System SHALL use a stricter threshold (e.g., 0.6 instead of 0.7).
3. WHEN video_duration > 60 minutes, THE System SHALL use a more lenient threshold (e.g., 0.8 instead of 0.7).
4. THE System SHALL log the effective deduplication threshold for each video.
5. THE System SHALL be configurable (adaptive thresholds enabled/disabled) via the Config object.

### Requirement 14: Clip Quality Confidence Score

**User Story:** As a user reviewing generated clips, I want to see a confidence score for each clip, so that I know which clips are most likely to perform well.

#### Acceptance Criteria

1. THE System SHALL compute a Viral_Potential score (0.0-1.0) for each selected clip.
2. THE Viral_Potential score SHALL combine: clip_score, hook_score, engagement_prediction, diversity_penalty.
3. THE System SHALL display the Viral_Potential score in the clip report (_why_chosen.txt).
4. THE System SHALL rank clips by Viral_Potential (in addition to clip_score) for user review.
5. THE System SHALL log Viral_Potential computation details for debugging.

### Requirement 15: Parser and Pretty Printer for Creator Profiles

**User Story:** As a developer, I want to parse and serialize Creator_Profile data reliably, so that profiles persist correctly across runs.

#### Acceptance Criteria

1. THE System SHALL implement a Parser for Creator_Profile JSON files.
2. WHEN a valid Creator_Profile JSON file is provided, THE Parser SHALL parse it into a Creator_Profile object.
3. WHEN an invalid Creator_Profile JSON file is provided, THE Parser SHALL return a descriptive error.
4. THE System SHALL implement a Pretty_Printer for Creator_Profile objects.
5. THE Pretty_Printer SHALL format Creator_Profile objects back into valid JSON files.
6. FOR ALL valid Creator_Profile objects, parsing then printing then parsing SHALL produce an equivalent object (round-trip property).

### Requirement 16: Configuration Validation

**User Story:** As a user, I want the system to validate configuration settings, so that invalid settings are caught early with clear error messages.

#### Acceptance Criteria

1. THE System SHALL validate all Config object fields on initialization.
2. WHEN a Config field is out of valid range, THE System SHALL raise a descriptive error.
3. THE System SHALL validate that scoring weights sum to 1.0 (within tolerance).
4. THE System SHALL validate that min_clip_duration <= max_clip_duration.
3. THE System SHALL validate that all file paths (Creator_Profile) exist and are readable.
6. THE System SHALL log all validation errors with field names and expected ranges.

### Requirement 17: Performance Optimization for Large Videos

**User Story:** As a user processing long videos (>2 hours), I want the system to remain performant, so that clip generation completes in reasonable time.

#### Acceptance Criteria

1. THE System SHALL process audio features in parallel (multi-threaded or multi-process) for videos >30 minutes.
2. THE System SHALL cache intermediate results (audio features, embeddings, LLM summaries) to disk for reuse.
3. THE System SHALL use efficient data structures (numpy arrays, sparse matrices) for large-scale computations.
4. THE System SHALL log processing time for each pipeline stage (transcription, scoring, selection, extraction).
5. THE System SHALL complete clip generation for a 2-hour video in <30 minutes on typical hardware (8-core CPU, 16GB RAM).

### Requirement 18: Error Handling and Graceful Degradation

**User Story:** As a user, I want the system to handle errors gracefully, so that one failure doesn't crash the entire pipeline.

#### Acceptance Criteria

1. WHEN the LLM_Scorer fails to connect to Ollama, THE System SHALL log a warning and fall back to text+audio scoring only.
2. WHEN the Emotion_Detector fails to load librosa, THE System SHALL log a warning and skip emotion detection.
3. WHEN the Semantic_Deduplicator fails to load embeddings, THE System SHALL log a warning and fall back to Jaccard deduplication only.
4. THE System SHALL continue processing remaining clips if one clip fails to extract or format.
5. THE System SHALL generate a summary report of all errors and warnings at the end of the pipeline.

### Requirement 19: Logging and Debugging Support

**User Story:** As a developer, I want comprehensive logging, so that I can debug issues and understand system behavior.

#### Acceptance Criteria

1. THE System SHALL log all major pipeline stages (transcription, scoring, selection, extraction) at INFO level.
2. THE System SHALL log all scoring decisions (text, audio, LLM, spike, burst, combined) at DEBUG level.
3. THE System SHALL log all LLM prompts and responses at DEBUG level.
4. THE System SHALL log all detected hooks, emotions, and diversity penalties at INFO level.
5. THE System SHALL log all configuration settings at startup.
6. THE System SHALL support configurable log levels (DEBUG, INFO, WARNING, ERROR) via CLI flag or config.
7. THE System SHALL write logs to both console and a log file (with rotation).

### Requirement 20: Documentation and User Guidance

**User Story:** As a new user, I want clear documentation, so that I can understand how to configure and use the improved clip selection system.

#### Acceptance Criteria

1. THE System SHALL provide a README section explaining the new clip selection features.
2. THE README SHALL include examples of Creator_Profile JSON files.
3. THE README SHALL explain how to enable/disable each feature (emotion detection, semantic deduplication, etc.).
4. THE README SHALL provide troubleshooting guidance for common issues (LLM connection, librosa installation, etc.).
5. THE System SHALL provide inline help text for all CLI flags (--help output).
6. THE System SHALL provide example configuration files for different content types (gaming, podcast, comedy).

### Requirement 21: Backward Compatibility

**User Story:** As an existing user, I want the improved system to work with my existing videos and configuration, so that I don't have to reconfigure everything.

#### Acceptance Criteria

1. THE System SHALL maintain backward compatibility with existing Config object fields.
2. THE System SHALL use sensible defaults for all new Config fields (so existing configs still work).
3. THE System SHALL detect and migrate old Creator_Profile formats to the new format (if schema changes).
4. THE System SHALL log a warning if deprecated config fields are used.
5. THE System SHALL continue to support the existing CLI interface (all existing flags work as before).

### Requirement 22: Unit and Integration Tests

**User Story:** As a developer, I want comprehensive tests, so that I can refactor and extend the system with confidence.

#### Acceptance Criteria

1. THE System SHALL include unit tests for all new scoring functions (Phrase_Detector, Emotion_Detector, etc.).
2. THE System SHALL include integration tests for the full pipeline (transcription → scoring → selection → extraction).
3. THE System SHALL include property-based tests for parsers (Creator_Profile round-trip properties).
4. THE System SHALL include tests for edge cases (empty transcripts, silent audio, LLM failures).
5. THE System SHALL achieve >80% code coverage for new code.
6. THE System SHALL run all tests in CI/CD pipeline (GitHub Actions or similar).

### Requirement 23: Performance Benchmarking

**User Story:** As a developer, I want to benchmark the improved system, so that I can measure performance gains and identify bottlenecks.

#### Acceptance Criteria

1. THE System SHALL include a benchmarking script that processes a set of test videos with different configurations.
2. THE Benchmarking script SHALL measure: total processing time, time per pipeline stage, memory usage, LLM call latency.
3. THE Benchmarking script SHALL generate a report (CSV, JSON, or HTML) with performance metrics.
4. THE Benchmarking script SHALL be runnable via CLI (e.g., python benchmark.py).
5. THE System SHALL log benchmark results to a file for historical tracking.
